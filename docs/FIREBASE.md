# Firebase and AI commentary setup

The app supports Firebase Email/Password Authentication, account-specific Firestore campaigns, immutable event documents and Gemini commentary through Firebase AI Logic. Without a configuration in `dist/firebase-config.js`, the original local demo still works.

## Population updates

The population feature supports all 234 countries and territories in the required Worldometers table, including microstates. Run `npm run dev` for local source checks at startup and daily while the server runs. The last validated response is cached outside `dist` at `.firebase/population-cache.json`, and `/population-data.json` serves it immediately to the local app. Existing games retain their original population and reward fields. Source checks pause when this server is off. Hosted clients use the bundled snapshot and public Firestore reference; GitHub's scheduled source checks remain inactive until their workflow is pushed.

The optional GitHub workflow `.github/workflows/populations.yml` is included in the GitHub backup. Its daily schedule runs when enabled in the repository Actions settings. The public reference `publicData/populations`, restricted updater account and encrypted GitHub Secrets have been configured and tested. A hosted/static client can read the reference without sign-in; only the dedicated updater can publish it. No administrator credential is stored in GitHub or the browser.

One-time setup after `npm ci` and `npx firebase login`:

1. Deploy the rules: `firebase deploy --only firestore:rules --project meridian-conquest-m112`.
2. Run `node scripts/configure-populations.mjs`. It uses the existing Git Credential Manager sign-in to encrypt two GitHub Actions Secrets, `POPULATION_UPDATER_EMAIL` and `POPULATION_UPDATER_PASSWORD`. The dedicated Firebase account has the `populationUpdater` custom claim. Rules exclude it from campaign and room access and allow it to update only the public reference document. No administrator credential is stored in GitHub or the browser.
3. Push the workflow to the default branch. In GitHub Actions, run **Update country populations** once and check its result. It subsequently runs daily at 05:23 UTC. Source errors leave the previous public document intact; GitHub's workflow log records the failure.

`npm run populations:update` refreshes the bundled offline snapshot without writing to Firebase. Redeploy Hosting to distribute a new bundle. The daily workflow updates the public reference automatically without a Hosting deployment. Missing rows, changed headers, noninteger counts, older timestamps/years and per-country changes over 25% are rejected. Review a legitimate large revision manually before replacing the baseline. Firebase remains on Spark; the job uses GitHub Actions minutes, not Cloud Functions. Disable the workflow to stop future source checks, or rerun the configuration script to rotate its password and GitHub Secrets.

## Gemini configuration

`dist/ai-config.js` contains public settings: the enabled flag, `gemini-3.6-flash` model name and reCAPTCHA Enterprise site key. There is no personal Gemini API key in the app. Firebase AI Logic handles authorization to Gemini through its managed proxy. The public Firebase key is restricted to Firebase services and cannot call the Gemini Developer API directly.

The connected project has the Gemini Developer API provider enabled, requires Firebase Authentication for AI requests and enforces App Check for Firebase AI Logic. The App Check service identifier is `firebaseml.googleapis.com`. The reCAPTCHA site key allows the two Firebase hosting domains. App Check enforcement for Authentication and Firestore has not been enabled by this setup.

Open the Settings gear to enable or disable **Gemini battle commentary**. This preference is stored on the device. Generation is enabled by default for signed-in gameplay. Turning the switch on during gameplay immediately requests recent action in the open campaign or hosted multiplayer match; subsequent saved events are narrated automatically. **Generate commentary** remains an optional retry, including for completed campaigns. Both entry points consider the latest three eligible events without current-version reports and select the most important pending event. Legacy reports can therefore be refreshed without overwriting or deleting them. Loading or reloading a campaign/room alone does not backfill history. Read-only snapshots and history views do not start requests from Settings. Only the host requests shared multiplayer reports; friends receive those reports automatically. The panel exposes queue, generation and actionable failure status.

For local development, run `npx firebase login` and `npm run dev`, then open http://localhost:8081. The server registers/reuses an App Check debug token under `.firebase/app-check-debug.json`, outside the public `dist` folder and ignored by Git. It supplies the token only from the loopback server, checks the request hostname, uses no-store responses and never prints it. Set `MERIDIAN_PORT` if 8081 is busy. The development server uses the pinned project-local Firebase CLI. Without an administrator CLI login, it still serves gameplay and saves; only local AI setup is skipped. Revoke its token in Firebase App Check when local development access is no longer wanted.

The public `dist/ai-local-config.js` is an empty stub. The development server overrides that URL in memory; no debug token is placed in a deployable file. The browser enables the debug provider only on loopback addresses. VS Code Live Server and other static servers can still play and save, but local commentary directs you to `npm run dev`. The live browser verification script instead registers an ephemeral debug token and deletes it during cleanup. See [Firebase's debug-provider guide](https://firebase.google.com/docs/app-check/web/debug-provider).

## Connect a different project

1. Sign in with `npx firebase login`, create a Firebase project and register a Web app. Keep the Spark plan if you want free quotas only.
2. Create Cloud Firestore and enable Email/Password Authentication. Add your hosting domains to authorized domains.
3. Copy the public Web app configuration to `dist/firebase-config.js` and select the project with `firebase use --add`.
4. In Firebase AI Logic, enable the Gemini Developer API provider. Configure Firebase Authentication requirements for AI requests.
5. Register your Web app with App Check using reCAPTCHA Enterprise, allow your hosting domains and enforce App Check for Firebase AI Logic.
6. Set the public site key and a supported free model in `dist/ai-config.js`. If changing the model, update the model allowlist in `firestore.rules` too.
7. Deploy with `npx firebase deploy --only firestore,hosting`. No Cloud Functions or billing upgrade is needed for this path.

`scripts/configure-gemini.cjs` is an idempotent setup helper for the connected Meridian project, using the existing Firebase CLI sign-in. It configures App Check, authentication requirements and the public Firebase key restrictions, and refuses to proceed if billing is enabled. It assumes the AI Logic provider is already enabled. Its project identifiers are specific to this project.

The older `functions/` implementation remains available as an optional server-side alternative. It is not deployed. That alternative requires an eligible billing plan and a Gemini key stored with `firebase functions:secrets:set GEMINI_API_KEY`; do not deploy it when staying on Spark.

## How it works

Signing in loads that account's campaigns and creates a separate browser recovery cache. Existing local demo campaigns are not silently uploaded into a new account. New campaigns save their board separately from their event history, avoiding the Firestore document-size limit for a growing history. Events have a sequence number and cannot be edited by browser clients. Large payload and typed-board fields are exempt from indexing. New records use schema version 2 with a structured board, immutable country-origin map and typed event facts. Legacy payloads remain readable and are dual-written for deployed older clients. There is no bulk campaign migration or event rewrite. See [database compatibility](../CONTRIBUTING.md#database-compatibility-and-security).

Campaign cards appear as soon as the board documents load, before long event histories finish downloading. Cached campaigns remain visible while loading or after a connection failure. Gameplay and cloud saves stay locked until all histories finish loading. Failed or stalled reads show a persistent error with **Retry loading**, rather than an empty campaign list. Reads time out after thirty seconds; late replies from an older load or account are ignored. The dashboard shows the signed-in email to help identify the account holding a save.

The commentary queue handles new attack, dice, retreat, held, conquest, elimination, victory and NPC decision events after their factual records are saved. Complete event snapshots stay in the queue; the Gemini request contains only the involved countries, event facts, event-time standings with preceding country counts, four recent event descriptions and two earlier wording examples. Lead changes are described explicitly so the model need not infer them from two full boards. Gemini 3.5 Flash-Lite uses minimal reasoning and a compact prompt asking for 12 to 28 words and at most 300 characters. The existing 60-word and 500-character storage limits remain compatible with older reports. NPC explanations come from the strategy engine. Each report is matched to its own event ID and displayed in the AI commentary tab without restarting dice animations or changing gameplay.

The report panel has **Field reports** and **AI commentary** tabs in campaigns and multiplayer. Factual events remain in Field reports; generated text, queue/error status and the optional Generate commentary control are in AI commentary. Switching tabs does not generate a request or alter the campaign. The active tab persists across game updates. Incoming reports update only the commentary list, preserving active inputs and dice animations, and hidden results still wait until the dice settle. The AI tab selects recent generated reports independently of the factual log's latest-event window, so quiet or skipped phases do not immediately push existing commentary out of view.

**Pin reports** optionally fixes the existing panel to the bottom of the screen within its map column. While expanded, the map scales proportionally to fit above the dock, with readable labels; shorter windows use a shorter report panel. Explicitly pinning or expanding brings the map into view when needed. Its arrow collapses or expands the content; selecting either tab also expands it. Collapsing or unpinning restores the map's original size, and **Unpin** restores the panel's original placement. Pin and collapse choices stay in UI memory across game renders and never enter saved campaign or room records. The panel reserves its measured height below the page so controls can scroll clear of it, follows column size changes and releases that space when unpinned or leaving gameplay. Incoming AI reports do not reopen a collapsed panel, change its selected tab or move the page.

New reports use impartial, third-person play-by-play for the whole match, including bot-versus-bot battles. The narrator calls the action between the countries and commanders involved, adds its immediate consequence and mentions the overall lead when that event changes it. It must not address the viewer, give advice or invent soccer mechanics. Battle context names both the attacker and the original defender from the attack snapshot, preserving their identities after conquest changes ownership. Saved nicknames remain unchanged; legacy "You" labels become neutral commander names only in AI context. Previously saved reports retain their original wording.

Each account and campaign/room keeps at most one pending event. Priority is victory, elimination, conquest, retreat/held, dice with casualties, attack, then NPC decisions or tied dice. Newer events replace pending events of equal priority; lower-priority arrivals are skipped. A higher-priority outcome also supersedes an in-flight report before generation or saving. Equal-priority in-flight reports can finish so continuous fast-forward does not suppress all commentary. Every factual event, dice result and NPC explanation remains visible, and gameplay never waits for Gemini. Requests batch up to six independent matches with at least six seconds between starts and a maximum of 12 pending matches. Timeouts and temporary model overload delay the next queued batch by five seconds; quota and other failures retain the one-minute cooldown. Failed events can be requested again with Generate commentary. There is no automatic historical backfill. Free Gemini quotas and availability still apply.

Current reports are stored once under `users/{uid}/games/{gameId}/aiReportsV2/{eventId}`, or `rooms/{code}/aiReportsV2/{eventId}` in multiplayer, with `narrationVersion: 2`. The original `aiReports` collections remain readable and unchanged. New-version reports take precedence even if an older listener replies later. **Generate commentary** can upgrade the most important of the latest three legacy or missing reports; the original version is preserved. Transactions reuse existing reports, and replays/reloads read saved results without generating them again. Up to three strictly earlier commentary snippets are supplied as wording memory, not factual evidence. Memory is bounded and isolated by account and campaign/room; late or later-event reports are excluded when narrating an older event. Concurrent browser tabs can still make duplicate model requests before either result is saved. Signing out discards queued work and late responses.

In multiplayer, only the host browser requests and saves commentary; friends receive the same reports through a Firestore listener. The host must keep the room open. Rejoining loads existing reports and starts generation only for subsequent events.

Dice results are calculated and saved immediately, while presentation keeps the preceding troop counts, ownership and field reports until the dice animation finishes. Loss reports, conquest and victory then appear together. Fast playback uses the shorter roll duration; reduced motion shows results immediately. The reveal does not change the dice, NPC decisions or stored game history.

## Access and current boundaries

Firestore rules isolate each user's campaigns. Unauthenticated visitors cannot write. Owners may create one AI report for an existing eligible campaign event; multiplayer reports may be created only by the host and read only by room members. Reports have a fixed schema, an allowlisted model and narration version, bounded text and a server timestamp, and cannot be updated or deleted by clients. The older server-only `commentary` collection still rejects client writes. Because generation runs through the browser, these rules cannot prove the text came from Gemini: a campaign owner or room host can submit their own report text. Commentary is advisory and never changes game state. Existing share links remain read-only embedded snapshots, not live Firestore subscriptions. Generated commentary already present in an embedded snapshot is not currently imported by the snapshot decoder.

Game moves and dice still run in the browser, and signed-in owners can submit their own campaign data. This integration provides authentication and cloud storage, not authoritative server-side anti-cheat enforcement. Avoid playing one campaign concurrently in multiple tabs or devices: board saves currently use last-write-wins. A failed initial account load keeps play locked rather than overwriting remote campaigns.

It creates two temporary accounts, tests access with their Firebase user tokens, and removes only its own test accounts and documents. Cleanup uses the Firebase CLI account's administrator access.

For read-only reproduction of an existing campaign, set `CAMPAIGN_TEST_PATH` to `users/<owner uid>/games/<campaign id>` and run `node scripts/campaign-load-browser-test.mjs`. It reads the saved board and history into memory, then tests rendering, loading failures, retry and cache recovery in an isolated browser with mocked Firebase writes. It does not modify the original campaign or account.

Run `node scripts/gemini-browser-test.mjs` to verify a real Gemini response, saved-report reuse and the settings toggle. It creates one temporary account and campaign plus an App Check debug attestation, then removes all of them. It requires Firebase CLI administrator access, the project-local Playwright package and a supported Chromium browser. Set `GEMINI_TEST_ORIGIN` to the hosting URL to check the published version. Set `GEMINI_TEST_STANDARD_APPCHECK=1` on that domain to exercise normal reCAPTCHA attestation instead of the debug provider.

With `npm run dev` running, `node scripts/commentary-preview.mjs` previews the narrator on human attack pressure, repeated tied dice, bot-versus-bot pressure and a bot capture that breaks a territorial tie. It checks third-person wording and that bot reports do not focus on an unrelated human commander. It uses the real browser SDK, prints generated lines and response time, and removes its temporary account without writing campaigns. `COMMENTARY_PREVIEW_ORIGIN` selects the development-server URL when port 8081 is busy, and `COMMENTARY_PREVIEW_MODEL` selects another model that supports minimal thinking for comparison. Timing includes initial SDK and App Check setup and varies with provider load. Model requests retain a thirty-second timeout. Existing Gemini 3.6 Flash reports remain readable, and the rules allow both models for version 2 reports.

## Multiplayer rooms

Open **Multiplayer** in the navigation. Sign in, create a room and share its six-character code. Friends enter the code to join the lobby. The host starts the match when everyone has joined; remaining seats become bots, for ten countries in total. Existing players can rejoin a started match with the same code; new players cannot join after the start.

Rooms use Firestore transactions and live listeners on the Spark plan. Each action checks the room revision to reject stale moves. Security rules restrict starts to the host and game updates to the current human player or the host for a bot turn. Version 2 rooms additionally validate structured board fields and freeze the original populations, reward values, country order and player roster. Lobby membership is limited to ten distinct accounts. Event history is append-only and the room document retains the latest eighty events for display. Older clients must refresh to a version 2 client before making moves in an upgraded room.

The host's browser runs the bots and must keep the room open. A disconnected human retains their seat, and the match waits for them when their turn comes. Host migration and automatic replacement of disconnected humans are not included. A host can close a lobby; players can leave before it starts. After starting, navigation away does not surrender a seat.

As with single-player gameplay, moves and dice are calculated in the browser. These room rules enforce membership, turn ownership and revision changes, but they do not validate every game calculation against an authoritative server. Use this version for games among trusted friends. A room code acts as an invitation: signed-in people who know it can read the room.

Multiplayer verification includes the automated room unit tests and a two-user desktop/mobile browser run: code joining, bot fill, lobby impersonation denial, active-turn permissions, shared attacks/dice, host-generated Gemini reports delivered to both players, report overwrite denial, automatic bot turns, reload reconnection and tab-close sign-out. Set `MULTIPLAYER_SKIP_AI=1` to verify gameplay without consuming Gemini quota or creating an App Check attestation. All temporary test data and any test attestations are removed by the script. `scripts/multiplayer-browser-test.mjs` uses the pinned project-local Playwright package and managed Chromium or installed Chrome. Set `MERIDIAN_BROWSER_PATH` to choose an executable. These are development tools, not browser runtime dependencies.
